Side-by-side comparison of the built V3 against the reference screenshots in
`reference/nvrmnd/` and the measurements in `context/reference-nvrmnd.md`.
Captured at 1440×900 (desktop) and 390×844 (mobile); overflow scanned at 1024,
1152, 1280, 1366, 1536 and 1920. Behaviour was exercised in a real browser
(hover, click, Escape, focus), not inferred from code.

Every number below was measured from the live DOM or from pixel samples of the

## Headline

The type scale matches the spec to the pixel (120/51/48/40/24/20/18/13). The
problems are not the sizes — they are **where** those sizes are used, **which
face** is used, and **what colour the grid is painted**. Four systemic
deviations account for most of what reads as "obnoxiously large", "irregular"
and "busy":

| # | Deviation | Reference | Ours |
|---|---|---|---|
| A1 | Pixel face used for every small label | Pixel face only on logo, chips, menu button, menu nav, step names, `Ø` numbers, wordmark. **Everything else — buttons, links, back-links, section labels, rail nav, socials, email — is the body face, uppercase, 14–18px** | Departure Mono 13px uppercase on all of it |
| A2 | Wrong *kind* of pixel face for display | Off-Bit: bold, proportional, wide pixel display | Departure Mono: thin monospace *text* face. At 48–276px it reads as terminal output |
| A3 | Grid rules painted at full strength | Renders as neutral `rgb(202,202,202)` — ~7% darker than canvas, whisper-quiet | Renders as full `rgb(36,103,236)` blue dots |
| A5 | Case-study statement scale | 33.6px in a 765px measure (~6 lines) | 51px in a 515px measure (**13 lines**) — a spec error in `design.md` §9.2 |

## A. Systemic — affects every page

### A1 · Display face in the wrong role
Measured on the reference home page and `/work/intellete`:

| Element | Reference | Ours |
|---|---|---|
| Primary CTA ("LET'S BUILD YOURS") | SF Pro 18px / 400, box 220×42 | Departure Mono 13px, box ~175×44 |
| Back link | SF Pro 18px, sentence case | Mono 13px uppercase |
| Section label ("Overview") | SF Pro 16px, sentence case, ink | Mono 13px uppercase, grey |
| Status pill | SF Pro 14px uppercase | Mono 13px uppercase |
| Bottom-rail items, socials, email | SF Pro 16px uppercase | Mono 13px uppercase |
| Rail scroll-spy items | SF Pro 16px | Inter 18px |
| Chip ("ABOUT US") | **Offbit 101 16px**, tracking 0.8px, height 29 | Mono 13px |
| Menu button | **Offbit 16px**, 103×44 | Mono 13px, 82×44 |

Rule to adopt: **pixel face = logo, chip, menu button, menu nav, step names,
`Ø` numbers, footer wordmark. Body face (uppercase, 14–18px) = every other
label, link and button.** Chips and the menu button are the only *small* pixel
text, and ours are smaller than the reference's there.

### A2 · Departure Mono is a text face, not a display face — **OWNER CALL**
Visible in the menu (96px), process step names (48px) and footer wordmark
(276px): narrow glyphs, monospace gaps (the "i" in `harisizm` sits in a cell as
wide as the "m"), thin strokes. The reference's Off-Bit is bold, proportional
and wide. Options: buy Off-Bit (`lessons.md` D-005, ~$70–90) or pick a free
bold proportional pixel face for the display role only (Pixelify Sans, Jersey
10/20, Silkscreen are candidates to mock up). Departure Mono can stay for any
small mono text that survives A1.

### A3 · Grid rules
Pixel samples at the x=368 boundary:

```
ours  .#.#.#.#.#.#.#.#.#.#   (36,103,236) on (217,217,217)  — full-strength blue dots
ref   averaged (202,202,202) on (217,217,217)              — faint neutral line
```
The reference declares the same blue; whatever it does to render it (alpha, a
different painted element), the on-screen result is a ~12% ink tint. Ours
should match the *rendered* result, not the declared colour.

Also:
- Overlays are per-section. The rule at x=368 is 8 separate segments with a
  **128px gap (8758→8886) above the footer** — the lines stop and restart.
  Reference: one continuous rule the full page height.
- Rules run through our footer. Reference footer has none; its rules end at
  the thin rule above "Quick Links".

### A5 · Statement measures
- Home positioning statement: 51px matches the reference. But the reference
  starts it at **column 2 with a first-line indent** and keeps the chip in
  column 1 on the same baseline; ours runs full-width from column 1 (6 lines
  vs 5).

  **51px, 515px wide, 13 lines**. `design.md` §9.2 wrongly reused the home
  statement scale here. This is the single largest "too big" offender.

### A6 · Case
The reference sets the hero, project titles, section headings ("HOW IT
WORKS", "SEE FOR YOURSELF", "INTELLETE", "WORDS-HURT") in **uppercase**. Ours
is sentence case throughout. Uppercase is what makes 120px read as a title
rather than a giant paragraph.

## B. Home

**B1 · Hero composition.** Reference: a *centred* block — 3-line uppercase
headline, first two lines bold and the last light (≈2/3 : 1/3), support
paragraph tucked top-right beside it, split CTA centred beneath, bottom rail
visible at y≈873 in the first viewport. Ours: left-aligned, 4 lines, only two
words bold (≈1/4 : 3/4 so the light weight dominates and looks flimsy at
120px), paragraph bottom-right, CTA bottom-left, content pushed to the bottom
(`justify-end`), hero 936px tall so the rail and scroll cue are below the fold.

**B2 · Positioning.** Reference: no heading on the rule-to-link (the rule
starts at column 2 and runs to "MORE ABOUT US ↗"); below it a body paragraph
with the pixel pointing-hand glyph, bold brand name, italic sign-off. Ours: a
"How I work" heading on the rule, an extra column-4 aside the reference does
not have, no body paragraph.

**B3 · Selected work.** Reference: **no section heading** — the section opens
straight on the first card. Card: chip + uppercase title at the top,
description pushed to the **bottom** (space-between), thumbnail row; image
spans **columns 2–4** (986×676); the whole card is one link. Ours: an extra
48px heading + "SELECTED WORK" chip, sentence-case title, description directly
under it, an extra "READ THE CASE STUDY ↗" link, image only in columns 3–4
(690px).

**B4 · Process.** Reference: heading + intro + "LEARN MORE ↗" in column 1;
the three steps in columns 2–4, **centred**: number / pixel name / body-face
20px subtitle / ~200px line-art diagram / centred body. Ours: heading across
the top, steps left-aligned in columns 1–3 with **column 4 empty**, subtitle in
mono 13px uppercase, no diagrams.

**B5 · Proof.** The "7" numeral sits 37px higher than its siblings (y 513 vs
550) because its sub-label wraps to two lines — baselines don't align. 32px
mono numerals read thin.

**B6 · Contact preview.** "START A PROJECT" is crammed directly under the card
paragraph (no gap, y 543 → 565); card 02's label has proper spacing.
Inconsistent.

**B7 · Footer.** Reference: thin rule → "Quick Links" + inline links (body
face) left, socials + `[ email ]` right → full-width rule → giant **uppercase
dotted-pixel** wordmark edge to edge → centred © line. No column rules. Ours:
three chip-labelled columns (MENU / CONTACT / SOCIALS) that do not exist in the
reference, all mono, **lowercase** mono wordmark with uneven monospace gaps,
left-aligned © line in mono, column rules running through, and the wordmark is
1410px in a 1408px box (clipped 2px at the "m").

## C. Menu

**C1 · Reticle geometry.** Arms are 16px with an 8px inset, so the four marks
nearly join into a full box. Reference: arms ≈12px, inset ≈24px — clearly crop
marks with air around the word.

**C2 · A second rectangle.** When the menu opens, the first item carries a
**2px solid lime outline** (a full rectangle) alongside the crop marks. It is
the focus-trap's programmatic focus triggering `:focus-visible`. It may not
appear after a real mouse click — verify — but it should never render as a
full box that fights the reticle; style the focus ring as the crop marks, or
suppress it when the menu is opened by pointer.

**C3 · Column placement.** Reference nav is right-aligned to column 2 (x≈655)
with contact in column 3. Ours: nav right edge x≈1010 (column 3), contact in
column 4. Shifted one column right.

**C4 · Open state.** See A4 — trigger and logo treatments differ.

**C5 · Right column.** Values (GITHUB, LINKEDIN, email, phone) in mono; the
reference uses the body face with icons.

**C6 · Verified working:** reticle moves on real hover (238 → 358, exactly
the WORK item), opacity 0.5 → 0.75, `Escape` closes, focus returns to the
trigger, `aria-expanded` toggles, body scroll restored.

## H. Cursors

Rendered side by side at 1×, 1.25×, 1.5× and 4× (`scratchpad/audit/cursor-compare-full.png`):

**H1 · Arrow.** Ours is heavier, the glyph only ~25px tall vs ~30px, and the
tail is a chunky detached block. Reference: thin arrow with a one-cell
diagonal tail stroke.

**H2 · I-beam.** Ours: thick stem, heavy caps — reads as a bold "I".
Reference: thin stem, wide thin caps.

**H3 · Pointer.** The biggest miss. Ours is a tall skinny index finger on a
tiny hand. Reference: a squat, wide hand with a cuff that fills the 32px box.

**H4 · "Not crisp / irregular".** Ours sets `shape-rendering="crispEdges"` on
a 2px cell grid. At Windows 125% / 150% the cursor is rasterised at 40 / 48px,
so each 2px cell becomes 2.5 / 3px and crispEdges snaps those unevenly —
alternating 2px and 3px steps, which is exactly "irregular". The reference has
no crispEdges (softer but even). Fixes, in order of effect: ship 2× assets via
`image-set()` in the `cursor` declaration; drop crispEdges; redraw on a 1px
cell grid. Hotspots are correct and the CSS is applied (`body`, `p`, `a` all
resolve to the custom URLs).
